# gridsearch

Homemade package for solving tricky numerical problems (e.g. politico-economic equilibria without closed-form solutions) via gridsearch/root-finding methods, shared across the model variants.

## Files
- `__init__.py` — imports `robustRoot`, `roots1d`, `cartesian`, `interp`, `continuation`; re-exports `CartesianGrid`, `griddedInterp1D`, `griddedInterp2D`, `griddedSmooth1D`, `griddedGradient1D`, `marchGrid`, `extrapolateX`.
- `testing.py` — the shared harness every `test_*.py` in the repo imports (`check`/`report`, plus a
  UTF-8 reconfigure of stdout/stderr on import — the model tests print Greek and Windows defaults a
  redirected stream to the ANSI codepage, which used to turn a passing suite into a `UnicodeEncodeError`).
  It lives in this package because `gridsearch` is the only importable one; the model folders are not
  packages. Not part of the numerical API and not re-exported by `__init__.py`.
- `robustRoot.py` — the bounded-root reparameterization from `writing/<model>/num_robustroot.tex` (`eq:root`): wraps a first-order-condition function `f` (only meaningful on `[l,u]`, e.g. a tax rate on `[0,1]`) into an unconstrained residual `h(z,τ)` that a gradient-based root-finder can search over all of `ℝ` without ever calling `f` outside its safe domain. Model-agnostic (takes `f` as a plain callable, no dependency on any specific model's `db`/`base.py`), so it's meant to be reused across `informalAnalytical`/`InformalSavings`/`US`'s policy solves, not just the one that motivated it.
  - `clip(τ, l=0, u=1)` — `[τ]_{[l,u]}`.
  - `penalty(τ, l, u, a0, a1)` — `g(τ)`, the out-of-bounds linear-penalty driver (0 inside `[l,u]`).
  - `boundedResidual(f, l, u, a0, a1)` — returns the callable `h(τ)`; `f` is only ever evaluated at `clip(τ,l,u)`. Recover the actual bounded policy from a solved `τ̃` via `clip(τ̃, l, u)`.
  - Verified against the doc's own worked examples (well-behaved interior root; both one-sided "always positive/negative on `[0,1]`" boundary cases) — reproduces the exact analytical roots (`τ̃=1+1/a1`, `τ̃=-1/a0`) the doc derives by hand.

- `roots1d.py` — one-dimensional root and extremum detection on a grid (`writing/<model>/num_peeLOG.tex`'s `alg:LOG:gridsearch`). Takes a sorted grid `x` (M,) and values `f` (M,) or (M,N) — N independent functions sampled on the *same* grid — and locates where the piecewise-linear interpolant of `f` crosses zero. Model-agnostic like `robustRoot`.
  - **Two families**, differing only in which crossings count. `allRoots`/`firstRoot` (`kind='any'`) for genuine root problems, where any crossing solves. `allMax`/`firstMax` (downward crossings) when `f` is the derivative of an objective and only maxima are admissible — e.g. the political FOC `z_t`, where an upward crossing is a local *minimum* of the political objective. `allMin`/`firstMin` for the mirror case. `allRoots` returns `(Kmax, N)` NaN-padded so the genuinely ragged result stays usable in vectorized downstream code.
  - **Exact zeros are always handled**, at any `tol`, via a sign-run rule (nodes with `|f| <= tol` are skipped when pairing signs). This is not an edge case: under `robustRoot` a corner solution is encoded as an *identically* zero value at an outer node (`h = z + |z| = 0` when `z < 0`), which `f[i]*f[i+1] < 0` cannot see. Zeros at the grid's own first/last node — precisely where corners land — get one-sided direction classification.
  - `tol` defaults to `0`: a nonzero default would report spurious roots wherever `f` merely grazes zero without crossing, which for maximum-detection is a real error rather than a rounding detail.
  - **Multiplicity**: `objectiveProfile(x, f)` is the cumulative trapezoid, which is the integral of the *same* piecewise-linear interpolant used to locate crossings — exactly, not approximately. `selectMax(x, f)` then returns the global maximiser over the candidate set `{x[0], x[-1]} ∪ {downward crossings}`, plus `nMax` (multiplicity flag) and `atBound`. This subsumes the boundary check rather than supplementing it: the endpoints compete with interior maxima on the same footing. Pass the *interior* grid only — outside `[l,u]` the penalised residual `h` is an artificial construction, not `dV/dτ`, so integrating it would be meaningless.

  - **Vectorized across columns.** `_matrixCrossings` detects crossings in every column at once, with no Python loop over columns. The one apparently-sequential part of the rule — "pair each node with the last *nonzero* node before it", whose reach varies by column and position — vectorizes via `np.maximum.accumulate` on the row indices, carrying forward the most recent nonzero node. Crossings are sparse, so the gathers and interpolation run only at the indices where one actually occurs (`np.nonzero`), which is what keeps the `(M,N)` temporaries down; compaction into the padded layout is a `lexsort` over the crossings alone, never over the full grid height. **4–8x** faster than looping in the intended range (`M ~ 10²` nodes, `N ~ 10²` states); the loop wins again past ~5·10⁶ elements, where cache locality beats fewer Python calls. `_columnCrossings` is retained as the readable statement of the rule and as the **test oracle** — the two are checked for exact agreement on 1200 randomized cases (400 inputs × 3 kinds), deliberately including zero runs, boundary zeros and all-zero columns.
  - **Ragged columns are grouped by feasibility pattern, not looped over.** `NaN` marks a node where the objective is genuinely undefined, and each column must be maximised over its own feasible sub-grid — which looks like it forces a per-column loop. It does not: columns sharing a `NaN` pattern share the sub-grid, so `np.unique(..., axis=1)` groups them and one vectorized call serves each group. Patterns are far from all-distinct in practice, because a grid search's feasibility usually depends on some state coordinates and not others — measured in `informalSavings`' CRRA recursion, **1–2 distinct patterns across 900 columns** per period, all of them ragged, so the pre-existing all-feasible fast path never fired and the loop ran 900 times where 1–2 calls suffice. Per column the result is bitwise what a single-column call returns (`allRoots` routes 1-column and many-column inputs through the same `_matrixCrossings`, whose every step is column-independent); `test_roots1d.py` asserts that against the per-column loop in both the few-patterns and all-distinct cases.
  - `selectMaxND(grid, f, name)` — `selectMax` over a `CartesianGrid`: searches along axis `name`, returns one solution per state combination reshaped to `grid.stateShape(name)`. Duck-typed (needs only `.values`/`.asColumns`/`.stateShape`), so `roots1d` stays a self-contained module about crossings on a grid with no dependency on how the grid was built.

- `cartesian.py` — `CartesianGrid`, the Cartesian product of named 1d grids and the flat↔ND mapping. Lets a grid search evaluate the model's equations **once**, on flat vectors covering every (choice, state) combination, then look along the choice axis alone. Numpy only.
  - **Why not a pandas MultiIndex** (as `inspiration/gridsearch` used, recovering the matrix via `unstack`): when the product is built here in C-order, the flat layout is fixed by construction, so `reshape` inverts it *exactly* and cheaply — no sorting, no label lookups, no dependence on `unstack`'s level ordering. Labels can still be attached for reporting; the solve path stays plain ndarrays.
  - `.flat` → `{name: (size,) vector}`, cached — feed straight in as `f(**g.flat)`. `.reshape(y)` → `shape + trailing`, so per-type `(points, ni)` arrays survive. `.asColumns(y, name)` → `(M, N)` for `roots1d`. `.stateShape(name)` → the shape a per-state result reshapes back to.
  - Nothing requires the choice axis to be first; `asColumns` moves whichever axis is named to the front.

- `interp.py` — four jobs on gridded data. `griddedInterp1D(x, y, kind='linear')`: a callable interpolant (e.g. a solved policy `τ(s)`/`h(s)`), evaluable at an arbitrary candidate state — thin wrapper around `scipy.interpolate.interp1d(..., fill_value='extrapolate')`, chosen over porting the inspiration's hand-rolled `CustomLinInterp`. **Extrapolates, does not clamp** — a candidate state from an outer root-solve need not land inside the grid. `griddedInterp2D(x, y, z, kind='linear')`: the same for a policy over *two* states (`RegularGridInterpolator`, extrapolating), evaluated **elementwise on paired coordinates** rather than on their outer product — the caller has one candidate `(s,ι)` per point, not a grid to cross. `griddedSmooth1D`/`griddedGradient1D(x, y, s, k, knots=None)`: a smoothing-spline denoise pass / derivative along a grid axis, sharing one fit (`_splineAlongAxis0`); NaN passes through per-column rather than poisoning the fit (real infeasible cells, not defensive padding). **`knots` decides whether the result is continuous in the data.** `None` keeps `UnivariateSpline(s=s)`, which lets FITPACK choose the knot *count* from the data — an integer that flips as the data moves, so the fitted profile jumps. An int `m` pins interior knots at every `m`-th valid node (`LSQUnivariateSpline`), making the fit a **linear map** of `y`, hence continuous, and ~2.4× faster since FITPACK stops iterating over knot counts. Pass an int wherever the output is differentiated with respect to a model parameter or feeds a root problem in one — the adaptive branch's knot flips read as genuine discontinuities there, and cost `InformalSavings` an uncalibratable parameter value until it was found (`notes/informalSavings_rho07_resolved.md`, `notes/crossCuttingFindings.md` #5). Default stays `None` so existing results reproduce bitwise.
  - **`kind` is load-bearing, not cosmetic** (added 2026-08-11). `'linear'` is the historical default and the only kind with no NaN handling to do. `'cubic'`/`'pchip'` remove the piecewise-linear kinks, which is what made `InformalSavings`' CRRA *calibration* solvable away from `ρ=1` at all — see item 14 of `notes/informalSavings_numericalDeviations.md` for the measurements. Prefer `'pchip'` on principle (monotone, `C¹`, cannot overshoot a policy that is flat at a bound, where `'cubic'` returns `[-0.088, 3.105]` on data spanning `[0,3]`) — but **`RegularGridInterpolator` rebuilds its pchip splines on every call**, 844 ms per 3600-point evaluation against 0.59 ms for `'linear'` and 1.02 ms for `'cubic'`. In 2-D that 1400× penalty rules it out until someone writes a precomputed bicubic-Hermite evaluator; in 1-D it is cheap.
  - **NaN survives the non-linear kinds** (added 2026-08-11). A policy surface carries NaN at infeasible nodes; `'linear'` propagates it for free, the spline methods refuse to be *constructed* over it. Invalid nodes are filled from their nearest valid neighbour for the fit and masked back to NaN on evaluation (`_validityMask`/`_fillInvalid`/`_maskedCall`), reproducing `'linear'`'s NaN pattern exactly off the nodes. **Do not "simplify" the mask away**: the fill is scaffolding for the fit, and without the mask an infeasible region returns a plausible-looking number instead of the non-finite value the caller's containment check is watching for. Separately, `RegularGridInterpolator` builds spline methods *lazily, per axis, at call time*, so a non-finite **evaluation coordinate** makes axis 0 return NaN and axis 1 then raise; both interpolants guard their coordinates. One inherited quirk is stated rather than reproduced: `interp1d`/`RGI` assign a point exactly on a node to the left-hand interval, so `'linear'` returns NaN at a *valid* node bordering an invalid cell where the masked kinds return the node's own value.
  - **Two traps that only show up once these feed a root-finder**, both found in `InformalSavings` and documented there (`writing/informalSavings/num_pee*.tex`, `notes/informalSavings_numericalDeviations.md`). *(i)* `griddedGradient1D`'s `s` is an **absolute** sum-of-squared-residuals bound, so one default cannot serve profiles of different magnitude — normalise per column before fitting. And where the underlying function has a known singular factor, differentiate in the coordinate that makes it affine (there: `ln(1-τ)`, worth ~13 orders of magnitude) rather than in the grid's own variable. *(ii)* A root located against `griddedInterp1D`/`2D` output inherits **kinks at the interpolant's own nodes**; a candidate grid that straddles them is worse than a coarser one that aligns with them. Refine such grids only in whole multiples of the interpolant's grid, or not at all.

- `continuation.py` — `marchGrid(grid, solve, ...)`: solve an expensive, ill-conditioned problem at every value of a parameter grid, using the solves already done to start the next one. Model-agnostic (callbacks in, records out; it never sees a `db`). Three properties the callers depend on, all asserted in `test_continuation.py`:
  - **Anchored and bidirectional.** `anchor` names the value solved first; the grid is then walked *outward from it in both directions*, each direction carrying its own history. Not a convenience — a problem that is only well-posed at one interior point (e.g. `ρ=1`, where a different and cheaper solver applies) has nowhere else to start.
  - **Extrapolation in the parameter value, not the grid index** (`extrapolateX`), through the last `degree+1` solves, componentwise, with the nodes centred on the target so the Vandermonde stays well conditioned. Index spacing stops being meaningful the first time step-halving inserts an off-grid value. The starting point should be an **unbounded** coordinate wherever the caller has one: extrapolating a positivity- or interval-constrained parameter in levels can step across its bound, giving a start that is invalid rather than merely poor.
  - **A retry ladder, then step-halving.** On failure: the un-extrapolated previous point first (extrapolating across a kink overshoots, and the previous point is both closer and cheaper than halving), then an intermediate value inserted between the last success and the target, solved and *kept* so the retry extrapolates from closer in. Failures are recorded, not raised — a sweep long enough to need this is too long to discard over one bad value — and `onPoint` fires per attempt so the caller can persist as it goes.

- `test_roots1d.py` — 79 assertions on `roots1d`, `cartesian`, and `interp` (interpolation accuracy, direction filtering, exact zeros on interior and boundary nodes, zero runs, `tol` behaviour, N-column vectorization, exactness of `objectiveProfile`, `selectMax` on multi-peaked objectives and corners, end-to-end integration with `robustRoot`'s corner encoding, the vectorized-vs-oracle equivalence sweep, `CartesianGrid` round-trips/column ordering/`selectMaxND`, and `griddedInterp1D`'s node-exactness/linearity/sorting/extrapolation/trailing-axis behaviour). `informalAnalytical/test_crraTerminal.py` covers the *integration* — `griddedInterp1D` actually feeding `CRRA.report_T`'s `τPolicy`/`hPolicy`.

- `test_interp.py` — 41 assertions on `interp`, concentrated on the NaN semantics the non-linear kinds had to preserve: the spline kinds' NaN pattern against `'linear'`'s own output off the nodes, no leak of filled values, non-finite *coordinates* returning NaN rather than raising, pchip's smoothness (7.3× smaller max second difference than linear) and its non-overshoot where cubic overshoots, trailing-axis invalidation, and the node-lookup quirk stated explicitly.

- `test_continuation.py` — 29 assertions on `continuation`, against deliberately fake solves so the checks are about *warm-start quality and failure recovery*, which a real solve would hide behind its own convergence: exactness of the extrapolation on linear/quadratic paths in both directions, degree fallback and the near-duplicate-node guard, anchored bidirectional visit order, the two directions not sharing a history, the retry ladder reached in order, step-halving carrying the march through values a direct step cannot reach, `minStep` terminating on a genuinely unsolvable value, and `onPoint` firing once per attempt.

## Implementation status
`robustRoot`, `roots1d` (incl. NaN/infeasibility handling in `selectMax`), `cartesian`, `interp` (all four functions, all three `kind`s) and `continuation` are implemented and tested. Consumed end to end by `informalAnalytical.policy` and by `InformalSavings.policy`'s `LOG` and `CRRA` classes (terminal period and the `t<T` backward recursion over one and two endogenous states respectively), and by `InformalSavings.model`'s `calibrateGrid`. `griddedInterp2D` is the only addition the two-state case needed — everything else transferred unchanged, which is the evidence that the package's interfaces are at the right level of generality. `US` has not started.

`testing.py` and `python/runTests.py` (the repo-wide runner) are infrastructure rather than numerics: the runner registers every suite in the repo, classifies it fast/slow by wall time, and runs each as a subprocess because the model suites mutate their instance's `db` and would collide in one process.

`continuation.py` is the first module here that is not about a single grid search but about *sequencing* many of them; it is in this package rather than in a model module because it never touches a `db`, and because the three model variants would otherwise each grow their own copy.

## Not ported from `inspiration/gridsearch` (deliberately)
The inspiration's `SolveGrid` class does a lot of work to precompute index maps and to avoid evaluating the full grid. Most of it addresses a cost this design removes, so it is being left out until something actually needs it:
- **Traversal order + per-state warm starts** (`_createTraversalOrder`, `GSLoop_i`) — exists because the inspiration solved state-by-state in a Python loop. Evaluating the whole Cartesian grid in one vectorized pass removes the loop, so there is nothing to warm-start.
- **`ΔL`/`ΔU` refinement + `estimate_refinement_from_full_solution`** — refinement exists to avoid evaluating the full grid, but a FOC evaluation's cost is dominated by per-call db overhead and is **flat in grid size** (`M=101` and `M=501` both ~1.8ms; see `informalAnalytical/README.md`'s "Base conventions"). Refining currently optimizes a non-problem. Revisit at `t<T`.
- **`fallback_to_nn`, `_fillNaN2D`, `_smooth2D_robust`** — handle infeasible state/choice combinations, which only arise at `t<T` once an *approximated* state can fall off-grid. Not reachable at the terminal period.
- **Index maps for `np.ix_` subsetting** — numpy `reshape` on a self-built C-order product is free, so these have no counterpart to earn.

What the precompute-once principle *did* justify is a cache of per-**year** db parameters — see `base.py`'s `cacheParams()`. That is the repeated cost here, and it is a model concern rather than a grid one.
